## technical

*(specific patterns about code, tools, builds, debugging)*

- **React: "seeded by prop, locally settable" state.** Don't write `useEffect(() => setState(prop), [prop])` — R19's `react-hooks/set-state-in-effect` rule rejects it. Instead, hold `override: T | null` in state and compute `display = override ?? prop` in render. Optimistic UI without the effect, and the override clears on settle. Applies to any prop-mirror with local edits (avatar URLs, form seeds, etc.).
- **Postgres RLS clause by command.** `SELECT` and `DELETE` policies use `USING`; `INSERT` uses `WITH CHECK`; `UPDATE` uses both (`USING` for which rows are visible to update, `WITH CHECK` for what the row may become). When a spec says "delete with check ..." treat it as intent shorthand and translate to `USING`.
- **Auth-gated mutations: return a result, don't throw.** For functions like `toggleLike` where the unauthenticated path is a *routine UI branch* (show sign-in prompt) rather than an exception, return `{ ok: true, ... } | { ok: false, code: "unauthenticated" | "failed", ... }`. The UI dispatches on `code` without a try/catch. Reserve throws for genuinely exceptional / programmer-error paths (e.g. helpers that hard-fail-closed like `uploadAvatar`).
- **Per-card auth state: ship the batched hydrator with the per-item action.** When a feed renders N cards each with auth-aware state (liked, count, owned-by-me, etc.), `Promise.all`-fetch the whole feed's state once in the parent and pass it down. The failure mode is invisible with a 3-row dev set — only at production scale do the N+1 round-trips bite. The batched helper is part of the feature, not a future optimization.
- **Cross-user readable profile fields belong in `public.profiles`, not `auth.users.raw_user_meta_data`.** The line is *"does another user's session need to read this?"*. `auth.users` is locked from `anon`/`authenticated` roles in Supabase, so anything a community feed or `/u/[username]` page must show requires a real table. Migrate with: create table → RLS (public read, own-row write) → `handle_new_user` trigger on `auth.users` for new signups → idempotent backfill (suffix-on-collision, NOTICE the suffixed rows) → strip the migrated keys from `user_metadata`. Keep small private fields (food_prefs, notification toggles) on `user_metadata` — that's still the right store for "only this user reads this".
- **Live profile sync without polling or Realtime: dispatch a window CustomEvent on write, listen for it in the hook.** The mutator (`upsertProfile`) fires `window.dispatchEvent(new CustomEvent("profile:updated"))` after a successful write; `useProfile` subscribes and refetches. Same-tab consistency without Supabase Realtime or a context provider; ~10 lines of code. Cross-tab needs a `BroadcastChannel`, but that's almost always out of scope for an MVP.
- **PostgREST embedded selects need a direct FK between the joined tables.** `from('a').select('..., b(...)')` only resolves if `a` has an FK to `b` (or vice versa). Chains through a third table (e.g. `ratings.user_id → auth.users(id) ← profiles.id`) don't resolve — PostgREST can't pick which path. Either add a parallel FK from the source to the target, or do two queries + a Map-keyed hydrator (`Promise.all` keeps the cost flat). In a codebase that already prefers flat selects + batched hydrators (likes, counts, raters), staying with two queries reads better than introducing a one-off embedded shape.
- **`notFound()` works in client components too — call it from render guarded behind a settled state.** In a client page that resolves data in `useEffect`, distinguish "still loading" from "fetched and missing" with two state flags (`loading: boolean` + `missing: boolean`). In render, branch `if (!loading && missing) notFound()`. The throw routes to the nearest `not-found.tsx` (or the framework's `/_not-found` default). Don't call `notFound()` from inside the effect — by spec it's intended to be called during render, and doing it from an effect can interact poorly with concurrent rendering.
- **Extract a shared component only for the call sites that need it today.** When you find a feed-item block duplicated across N pages, resist the urge to unify all N at once — chances are at least one site (History's edit affordance, Dashboard's "Top Rated" callout) has shape divergence that will force a prop explosion or a fork later. Extract for the 1-2 sites that match exactly, leave the others inline with a top-of-file comment pointing at the spec for future convergence. Premature unification locks in the wrong abstraction.
- **Next.js `useParams()` returns the *undecoded* URL segment in client components.** A `<Link href="/u/mark grout">` becomes `/u/mark%20grout` in the browser; `useParams<{username:string}>()` then hands you `"mark%20grout"`, not `"mark grout"`. Pass that into `.eq("username", ...)` and you'll spuriously 404 against a row that's actually there. Wrap every useParams read that drives a DB lookup with `decodeURIComponent` inside a try/catch (it throws on malformed sequences like a lone `%`). See vercel/next.js#64952 — the inconsistency between `page.tsx`/`useParams` (undecoded) and `route.ts` (decoded) is not on track to be unified. Bonus: constrain identifier columns to a URL-safe alphabet (`^[A-Za-z0-9_-]+$`) at the input layer when you can — it sidesteps this gotcha entirely.
- **App-wide visual overhaul: flip at the token layer, not the component layer — but verify the *contrast contract* between paired tokens.** When components route through semantic Tailwind tokens (`bg-surface-container-low`, `text-on-surface-variant`, `text-primary`, `bg-primary-container text-on-primary-container`, etc.), an entire restyle is a 3–4 file diff against `@theme inline` + the underlying palette CSS — components don't need to change. Pre-flight `rg "bg-(red|green|...)-[0-9]"` and `rg "dark:"` to confirm the discipline holds before committing to the strategy. Two contrast traps to verify *during* the remap: (a) **paired tokens** like `primary-container`/`on-primary-container` and their `:hover` swap to `primary-fixed` must keep readable contrast on every state — the original palette's "saturated bg + light text" can silently invert to "light bg + dark text" on rest and "dark bg + dark text" on hover if you remap each in isolation; (b) **container tier ramps** (`surface-container-low` → `hover:surface-container` → `surface-container-high`) must stay visibly differentiated, because hover effects collapse to nothing when both ends of a swap resolve to the same colour. Same brand colours read very differently against dark vs light backgrounds: a brand amber that pops against near-black at 14:1 may fail AA against cream at 2.4:1 — re-pick text colours for the *new* substrate even if the brand swatch hasn't changed.
- **State machines: discriminated unions beat parallel boolean flags.** When a feature has more states than `{loading, error, data}` — e.g. permission gating, cache layers, async fetch, and a downstream filter all gate the same UI region — model state as a single `type State = { kind: "probing" } | { kind: "needsPermission" } | { kind: "fetching" } | { kind: "results", venues: T[] } | { kind: "empty" } | { kind: "error" } | { kind: "hidden" }` and switch on `state.kind` at render time. Three wins that compound: (1) the render becomes an exhaustive case match — TypeScript will catch any new state you forget to handle; (2) "what's the UI right now" is answerable from a single field, not from inferring across `loading && !error && results.length > 0 && permissionGranted && !filterPending`; (3) impossible states (e.g. `fetching === true` AND `results.length > 0`) become unrepresentable rather than a runtime bug waiting to surface on a slow network. Same pattern as `ToggleLikeResult` in `lib/ratings/likes.ts` (auth-gated mutation result discriminated by `code`); when in doubt, copy that shape.
- **`react-hooks/set-state-in-effect` only fires on setState calls in the effect's *direct* lexical scope, not inside a nested async function.** If you write `useEffect(() => { async function init() { setState(...); /* ...await... */ } void init(); }, [])`, the rule does *not* flag the inner `setState` — adding an `eslint-disable` directive there will produce an "unused directive" warning. The lint baseline matters: the rule still catches the simple `useEffect(() => { setLoading(true); fetchData(); ... })` pattern (which is what the two long-standing baseline errors in `(main)/page.tsx` and `(main)/history/page.tsx` are). When you need the synchronous `setLoading(true)` UX (skeleton appears immediately, async work follows), wrap the entire body in an async IIFE so the setState is no longer at the effect's top lexical level.
- **Next.js client components + `useSearchParams` need a Suspense boundary even when `"use client"`.** Static prerender still tries to render the page, and `useSearchParams` throws if it's not inside `<Suspense>`. The fix pattern (used by `/onboarding/signup`, then `/rate`): default-export a thin wrapper that renders `<Suspense fallback={…}><PageInner /></Suspense>`; move the page body into `PageInner` and read `useSearchParams` there. Fallback should be a sized placeholder matching the page's first-paint shape so the SSR→hydration handoff doesn't flicker.
- **Deep-link query params consumed by an effect: gate with a parent-state "consumed" flag, not just an internal ref.** When a `?placeId=...` deep-link auto-fires a Place Details fetch in a child component on first mount, you need both: (a) an in-component `useRef` guard to make the auto-select effect idempotent across re-renders with the same prop, AND (b) a parent `useState` "consumed" flag so a *remount* (e.g. user clicks "Change" → spot toggles to null → child key flips → fresh child instance) doesn't re-auto-select the same stale URL value. Without (b) the user clicking "Change" to pick a different venue gets the original deep-link venue auto-selected again — and Place Details is a paid SKU so the re-spend is real. Compute the prop as `consumed ? undefined : queryValue ?? undefined` and flip `consumed` to true inside the parent's `onSelect` handler; safe to call unconditionally on subsequent selects (already-true is a no-op).
- **When a third-party API hands you structured data alongside what you came for, capture all of it at ingest.** Retrofitting derived fields later means either re-paying the API per row (Place Details is ~$22/1K including atmosphere SKU) OR parsing freeform text the API also gave you in structured form for free. The cost asymmetry is severe — capturing `address_components` and `price_level` on the *same* Place Details call you already pay for costs nothing extra in the Basic Data SKU and ~$5/1K extra for Atmosphere Data; recovering them weeks later requires a full Place Details re-query per unique place, plus a write-side migration script. Rule: when integrating a paid API (Google Places, Mapbox, Stripe, Twilio, etc.), list every field the response carries and decide column-by-column "could we possibly want this for analytics, search, or SEO?" The defaults should bias toward capture. Storage is cheap; API recalls are not. Surfaces this in `/rate`'s Place Details call (added cuisine + structured address + price_level alongside the existing name/address/types capture).

## process

*(patterns about how to work — scoping, clarification, sequencing, when to ask)*

- **Sticky items drain FIFO on the next implementation iteration unless the user explicitly says otherwise.** `work.md`'s `## sticky` section is not an indefinite parking lot — anything the user parks there has already been judged worth doing, and leaving it untouched while taking on new ad-hoc work forces them to re-raise it (which is exactly the token spend they parked it to avoid). When the user opens a new implementation task, default behavior is: check sticky → drain the top item first (or bundle with the new ask if related), then do the new ask. Only skip sticky when the user explicitly says "skip sticky," "do X first," or "hold for later." Discussion-only / planning turns don't count as iterations and don't trigger sticky drain — only a coding/implementation request does. Caught when "subtler Founder pill" sat in sticky for several iterations of unrelated rating-system work and the user had to re-raise it.

## costly mistakes

*(things that wasted real time. these earn their keep by preventing repeats)*

- **Supabase `upsert` with a partial column set.** Fails on tables with NOT NULL columns that aren't in the payload, even when the row already exists. PostgreSQL evaluates NOT NULL during INSERT row construction, before `ON CONFLICT` can route to the UPDATE branch. Use plain `.update().eq('id', ...)` for partial patches; reserve `upsert` for cases where every NOT NULL column is in the payload.
- **Absolute-positioned overlay on a shared component silently collides with whatever else lives in that region.** When wrapping a component you don't own (or one you've recently extended in the same session) with an `absolute right-X top-Y` decoration, you claim a screen region without telling the underlying component you took it — neither TypeScript nor lint catches the overlap. Hit this when `FeedRatingCard` added a guest-only Follow overlay at `right-md top-md` of `RatingCard`, landing directly on top of the `FounderBadge` that had been added to `RatingCard`'s top-right in the previous workstream. The fix that should have been the first instinct: add a named slot prop to the underlying component (`trailingAction?: ReactNode` rendered in normal flow next to `LikeButton` via `justify-between`), and have the wrapper pass through the slot. Slots are auditable in one place, survive future layout changes, and compose via props instead of stacking. Rule: when reaching for `absolute` on a shared component, stop — name a slot on the component instead. Reserve overlay positioning for components whose layout you fully control and whose extension surface you don't expect to grow.
